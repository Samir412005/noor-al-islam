# نور الإسلام — بوت تيليجرام إسلامي (NoorIslamBot)

بوت تيليجرام عربي يعمل ببنية **وكلاء متعدّدين** (Multi-Agent)، يقدّم النصوص الشرعية
بمصادرها: القرآن وتفسيره، الحديث بتخريجه، الأذكار والأدعية، مواقيت الصلاة والقبلة
والتاريخ الهجري، والمناسبات الإسلامية، إضافة إلى **وكيل العلم** الحواري الذي يجمع
النتائج من كل المصادر.

كُتب البوت بـ Python (aiogram) على مبدأ واحد: **نقلٌ بمصدر، لا إنشاء نصّ ولا فتوى**.
ويعمل كاملاً **دون أي مفتاح ذكاء اصطناعي**؛ فالمفتاح يوسّع الحوار فقط ولا يمسّ صميم النصوص.

---

> ## ⚠️ تنبيه شرعي مهم — اقرأه قبل أي شيء
>
> **المحتوى الشرعي في هذا البوت مُجمَّعٌ آلياً من مصادر منشورة على الإنترنت (تفسير،
> متون حديث، أذكار، حسابات فلكية للمواقيت). هذا التجْمِيع لا يرقى إلى تحقيقٍ علمي
> ولا إلى مراجعةٍ من أهل العلم، ويلزمه عرضٌ على أهل الاختصاص قبل أي استعمال عام.**
>
> البوت **لا يُفتي** ولا يُحلّل ولا يُحرّم، ولا يُصدر ترجيحاً بين الأقوال. غايته أن
> يقرّب النصّ إلى القارئ مع مرجعه، والحكم الشرعي مردّه إلى دار الإفتاء أو عالم موثوق.
> والمناسبات الهجرية تُحسب **حسابياً** وقد تخالف الرؤية بيوم. المستخدم مسؤول عن
> التحقّق قبل الأخذ أو النشر.

## ما الذي يميّزه

- **بنية وكلاء متعدّدة منفصلة عن طبقة تيليجرام**: كل وكيل يعيد كائن `AgentReply`
  مستقلاً، وهذا يجعل الوكلاء قابلين للاختبار بلا بوت ولا شبكة.
- **حواجز حماية صريحة (guardrails)**: كشف أسئلة الفتوى، كشف النسبة بلا مرجع،
  وردود خاصة لأسئلة إيذاء النفس والسحر والطائفية.
- **الأدوات إلزامية في مسار الذكاء الاصطناعي**: وكيل العلم لا «يحكي» آية أو حديثاً،
  بل يستدعي أدوات القرآن والحديث ويقتبس نتيجتها حرفياً، ثم يُفحَص ردّه بعد ذلك.
- **العمل دون إنترنت أو دون مفتاح**: القرآن والأذكار مُجمَّعان محلياً، وكتب الحديث
  تُخزَّن على القرص بعد أول تنزيل، ووكيل العلم يتحوّل تلقائياً إلى بحث متعدّد المصادر.
- **تخزين مؤقت متدرّج**: كاش TTL في الذاكرة + كاش كتب الحديث على القرص.

### قائمة الأوامر المسجّلة في تيليجرام

مأخوذة حرفيّاً من `COMMANDS` في `app/bot.py`، وتُسجَّل عند الإقلاع بـ`set_my_commands`
بنطاق `BotCommandScopeAllPrivateChats`:

| الأمر | الوصف |
|---|---|
| `/start` | رسالة البداية 🕌 |
| `/menu` | القائمة الرئيسية |
| `/quran` | 📖 وكيل القرآن |
| `/hadith` | 📜 وكيل الحديث |
| `/adhkar` | 📿 وكيل الأذكار |
| `/prayer` | 🕌 المواقيت والقبلة |
| `/occasions` | 🌙 المناسبات القادمة |
| `/ask` | 🧠 اسأل وكيل العلم |
| `/city` | 📍 تحديد مدينتك |
| `/settings` | ⚙️ الإعدادات |
| `/help` | 📘 المساعدة |
| `/about` | ℹ️ عن البوت |

هذه هي مفاتيح الموجّه نفسها في `app/router.py`، ويقبل كل أمر مرادفاً عربياً (`/قرآن` ·
`/حديث` · `/أذكار` · `/مواقيت` · `/مناسبات` · `/اسأل`). وهناك أوامر إضافية يعالجها
`app/handlers/commands.py` و`app/handlers/admin.py` وإن لم تُدرَج في القائمة المسجّلة:
`/id` و`/agents` للجميع، و`/stats` و`/broadcast` **للمشرفين فقط** (المعرَّفون في
`ADMIN_IDS`).

## المبدأ الأخلاقي والعلمي (أهمّ ما في المشروع)

هذا المبدأ مُنفَّذ في الكود لا في الشعارات، عبر `app/guardrails.py` و
`app/agents/scholar.py`:

1. **لا فتوى.** أي سؤال يُطابق أنماط الحكم الشرعي (`حكم`, `هل يجوز`, `حرام`, `طلاق`,
   `ميراث`, `كفارة`, `تكفير`…) يُقابَل بردٍّ صريح: «أنا ناقلٌ لا مُفتٍ»، مع الإحالة إلى
   دار الإفتاء أو عالم موثوق، وعرض النصوص المتّصلة إن وُجدت.
2. **لا نصّ بلا مصدر.** كل آية وحديث يُعرضان مصحوبين بمرجعهما (السورة: الآية، أو
   الكتاب + رقم الحديث). وكل ردّ من مسار الذكاء الاصطناعي يمرّ على
   `apply_output_guard`: فإن ظهرت فيه نسبةٌ للنبي ﷺ أو لله تعالى **بلا تخريج ولا مرجع**،
   يُلحَق به تحذير ظاهر: «لم أجد مرجعاً مرفقاً لهذا النص…».
3. **لا اختراع حديث.** وكيل الحديث لا يولّد نصاً؛ إن لم يجد الحديث قال «لم أجد» صراحة،
   ويأخذ المتن والتخريج من المصدر حرفاً بحرف. ووكيل العلم مُلزَم — في تعليماته
   النظامية وفي أدواته — بأن يقتبس من نتائج الأدوات، وإن لم تُرجِع الأداة نصاً قال ذلك.
4. **حذرٌ في المواضع الحسّاسة.** أسئلة إيذاء النفس تُقابَل بردٍّ رحيم مع أرقام
   الطوارئ وآية {وَلَا تَقْتُلُوا أَنفُسَكُمْ}؛ وأسئلة السحر والغيب بالتوكّل والرقية
   المشروعة والتحذير من المشعوذين؛ والنياشين الطائفية بالاعتذار والإعراض عنها.
5. **فحص المدخل قبل الوكيل.** يُستدعى `precheck()` في الحواجز فعلاً من
   `app/handlers/core.py` لفحص الرسالة *قبل* التوجيه (إيذاء النفس / السحر / الطائفية)،
   ووكيل العلم يستعمل الفحص نفسه داخل معالجه.

## التشغيل السريع

المتطلَّبات: Python 3.10+ (الصورة الرسمية في `Dockerfile` تستخدم 3.12).

```bash
python -m venv .venv
source .venv/bin/activate          # في ويندوز: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# املأ BOT_TOKEN من @BotFather، وADMIN_IDS من @userinfobot عند الحاجة

python scripts/fetch_quran.py      # ينزّل نصّ القرآن كاملاً → app/data/quran_uthmani.json
python scripts/fetch_adhkar.py     # ينزّل «حصن المسلم»      → app/data/adhkar.json

python -m app.main                 # تشغيل البوت (RUN_MODE=polling افتراضاً)
```

- **كتب الحديث** لا تحتاج أمراً مسبقاً: تُنزَّل تلقائياً عند أول طلب، وتُخزَّن في
  `data/cache/hadith/ara-<الكتاب>.json` فتعمل بعدها بلا شبكة.
- **القرآن والأذكار** يعملان بلا شبكة إن وُجد الملفان المذكوران (وإلّا يلزمهما التنزيل).
- **التفسير والصوت والمواقيت والقبلة** تحتاج إنترنت (خدمات خارجية).
- `make run` و`make test` مختصران موجودان في `Makefile`.

### حالة المستودع الحالية

المشروع **مكتمل ومربوط بتيليجرام فعلاً**: `app/main.py` هو نقطة الدخول
(`python -m app.main`)، ويعمل بوضعَي `RUN_MODE=polling` (افتراضاً) و`RUN_MODE=webhook`
(عبر `aiohttp` و`SimpleRequestHandler`)، ويسجّل الأوامر والوصف عند الإقلاع عبر
`set_my_commands` و`set_my_description` و`set_my_short_description`. طبقة المعالجات
كاملة في `app/handlers/` (الأوامر والقوائم وأزرار الوكلاء والنصّ الحرّ وأوامر المشرف)،
ويحقن `app/middlewares.py` ملفّ المستخدم ويحجز الأخطاء، ويعمل الموجّه والوكلاء والحواجز
كما هو موثَّق أدناه. كل ما في هذه الوثيقة مطابق للكود في `app/`، وتفاصيل الطبقة في
`docs/ARCHITECTURE.md` (قسم «طبقة تيليجرام»).

### الإشعارات المجدولة (`DAILY_PUSH`)

عند `DAILY_PUSH=true` يُشغّل `app/main.py` مهمّة خلفية (`app/scheduler.py`، دورة كل ٦٠
ثانية) تُرسل للمشتركين، بتوقيت كل مستخدم (`UserProfile.tz`)، الإشعارات التالية:

| الإشعار | الساعة | الوكيل | التفضيل المطلوب |
|---|---|---|---|
| مواقيت اليوم | ٥:٠٠ | `prayer` | `push_prayer` |
| أذكار الصباح | ٦:٣٠ | `adhkar` | `push_adhkar` |
| آية اليوم | ٨:٠٠ | `quran` | `push_quran` |
| أذكار المساء | ١٨:٣٠ | `adhkar` | `push_adhkar` |

- الجدول الفعلي في `SCHEDULE` بـ`app/scheduler.py`، ومنع التكرار عبر جدول `push_state`
  في قاعدة البيانات بالمفتاح `(chat_id, kind, day)`.
- لا يُرسَل الإشعار إن كان `UserProfile.daily_push=false`؛ ويمكن للمستخدم إيقافه من
  «⚙️ الإعدادات» ← «🔔 الإشعارات» (الزرّ `set:push`).
- تحتاج الإشعارات **عملية دائمة** (لا تعمل إن كانت الخدمة مُوقَفة) — حتى في وضع
  webhook؛ التفصيل في `docs/DEPLOY.md`.

### الاختبار الدخاني (smoke)

```bash
python scripts/smoke.py            # ٢٣ حالة حقيقية عبر مسار المعالجة الكامل (يحتاج شبكة)
python scripts/smoke.py --offline  # نفس الحالات بلا شبكة (الشبكة مُبطَلة بالحقن)
```

يمرّر `scripts/smoke.py` الحالات عبر `app.handlers.core.process_text` (بلا تيليجرام)،
ويطبع لكل حالة الوكيل الذي وُجّهت إليه وعدد الأزرار والصوت والمصادر، ثم ملخّص
«النتيجة: N/N» ورمز خروج غير صفري عند أي فشل. عدد الحالات مُعرَّف في `CASES` داخل
السكربت.

## تفعيل الذكاء الاصطناعي (اختياري)

وكيل العلم يعمل بمسارين: بلا مفتاح (بحث متعدّد المصادر) وبمفتاح (حوار + أدوات).
الشرط في `app/config.py` – `llm_enabled`: وجود `LLM_BASE_URL` و`LLM_MODEL`، مع
`LLM_API_KEY` أو عنوان محلي (`127.0.0.1` / `localhost` / `0.0.0.0` / `host.docker.internal`).

| المزوّد | `LLM_BASE_URL` | `LLM_MODEL` | `LLM_API_KEY` |
|---|---|---|---|
| OpenRouter | `https://openrouter.ai/api/v1` | `meta-llama/llama-3.3-70b-instruct:free` | مطلوب |
| Groq | `https://api.groq.com/openai/v1` | `llama-3.3-70b-versatile` | مطلوب |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` | مطلوب |
| Ollama محلي | `http://127.0.0.1:11434/v1` | `qwen2.5:7b` | غير مطلوب |

**بدون أي مفتاح**: البوت كامل الوظائف في القرآن والحديث والأذكار والمواقيت والمناسبات،
ووكيل العلم يتحوّل إلى بحث فوري في المصادر الثلاثة (القرآن، الحديث، الأذكار) ويعرض
النصوص بمراجعها. وإذا كان المفتاح مضبوطاً لكن الخدمة معطّلة، يسقط البوت تلقائياً إلى
المسار نفسه مع إشعار المستخدم بأن نتائج البحث المباشر هي المعروضة.

## الأوامر وعناصر القائمة واختصارات الأزرار

آلية الأزرار في المشروع هي **`callback_data` بصيغة موحّدة** يفكّها الموجّه:

```
ag:<agent>:<action>[:arg1[:arg2…]]
```

مثال: `ag:adhkar:item:12:3` = وكيل الأذكار ← عرض العنصر ٣ من الباب ١٢.
وحدّ تيليجرام 64 بايت، ولذلك يقصّ `Button.callback_data` الوسائط ويستخدم وكيل الحديث
اختصارات مؤقّتة (`~1`, `~2`) للاستعلامات الطويلة.

| الاختصار | ماذا يفعل |
|---|---|
| `ag:prayer:timings` | مواقيت الصلاة اليوم (زر «تحديث») |
| `ag:prayer:monthly` | تقويم الشهر كاملاً |
| `ag:prayer:next` | الصلاة القادمة / المتبقّي لها |
| `ag:prayer:qibla` | اتجاه القبلة |
| `ag:prayer:hijri` | التاريخ الهجري |
| `ag:quran:random` | آية أخرى (من قائمة مختارة) |

## 🛡️ الحارس (Noor Guardian) — من يراقب البوت؟

خدمة **مستقلّة** عن البوت تراقبه كل ٣٠ ثانية، وتُصلح الأعطال بنفسها، وتُنبّهك عبر
قنوات لا تعتمد على البوت نفسه. الفكرة: «من يراقب المراقب؟» ⇒ ثلاث طبقات:

```
① البوت نفسه      : ثلاث عمليات + مشرف (يعيد الميّتة في ٠.٥ ث)
② الحارس (guardian): 13 فحصاً + إصلاح تلقائي + تنبيه   ← خدمة منفصلة
③ المستوى الثاني    : يراقب *نبض* الحارس ويعيده إن تجمّد (scripts/level2_watch.sh)
```

**الفحوصات الـ13:** المشرف · الحراسة الدقيقة · عمليات الخدمة · الفحص المحلي ·
**الوصول من الإنترنت** · **مطابقة الويب هوك** · **اختبار المسار الكامل** (يحاكي تحديث
تيليجرام فعلياً) · ملفات البيانات · القرص · الذاكرة · سلامة قاعدة البيانات ·
مزوّد الذكاء · بوت الحارس. ولكل فحص إصلاح محدّد (إعادة مشرف/عمليات/إعادة ضبط الويب هوك/
إعادة توليد البيانات/تقليم السجلّات/إصلاح القاعدة/إيقاف الذكاء المعطوب).

**قنوات التنبيه (مرتّبة بحسب الخطورة):** بوت الحارس الخاص (إن وُجد توكن) ← تقويم Google
← البوت الهدف ← مسودّة Gmail. عند العطل الحرج **لا نعتمد على البوت** — التقويم يوصلك.

```bash
bash scripts/run_guardian.sh                 # تشغيل الحارس (مشرف + حلقة)
python -m guardian.daemon --status           # تقرير الآن
python -m guardian.daemon --once --force-fix # دورة واحدة بإصلاح فوري
python -m guardian.daemon --selftest         # فحص قنوات التنبيه
python scripts/guardian_drill.py             # تدريب: يُحقن أعطالاً حقيقية ويتحقّق من الإصلاح
bash scripts/level2_watch.sh                 # الطبقة الثالثة (تُستدعى من cron)
```

**نتيجة التدريب الفعلي** (`guardian_drill.py`): **٤/٤ أعطال أُصلحت تلقائياً** —
قتل عملية خدمة · قتل المشرف والحراسة · **إفراغ الويب هوك** (العطل الذي جعل البوت صامتاً)
· فقدان ملف بيانات.

> **خطوة يدوية واحدة لا يستطيع أي وكيل فعلها:** إنشاء «بوت الحارس» عبر `@BotFather`
> ثم وضع التوكن في `GUARDIAN_BOT_TOKEN`. بدونه يعمل الحارس كاملاً ويُنبّه عبر التقويم
> والبوت الهدف — التوكن يُضيف قناة أسرع وتحكّماً تفاعلياً (`/status` `/fix` `/restart`
> `/logs` `/incidents` `/mute`).

التفاصيل الكاملة في [`guardian/README.md`](guardian/README.md).

## التوفّر: لماذا لا ينقطع البوت

البنية تعتمد ثلاث عمليات تتقاسم نفس المنفذ (`SO_REUSEPORT`) ومشرفاً يعيد الميّتة خلال
نصف ثانية، مع حراسة كل ٦٠ ثانية:

```
        تيليجرام
            │  webhook (سرّ إلزامي)
            ▼
   ┌────────────────────────┐
   │  المنفذ 8080 (مشترك)    │
   ├────────┬────────┬──────┤
   │ worker │ worker │worker│   ← إحداها primary تتولّى الإشعارات المجدولة
   │  #1    │  #2    │  #3  │
   └────────┴────────┴──────┘
            ▲
     المشرف يعيد الميّتة (0.5ث) · الحراسة الدقيقة (60ث) · حارس وكيل (30د)
```

**قياس فعلي على هذا المشروع** (`python scripts/measure_availability.py`):

| السيناريو | قبل | بعد |
|---|---|---|
| قتل عملية واحدة | توفّر 51% · انقطاع 8.8 ث | **100%** · أطول انقطاع **0.37 ث** |
| قتل عمليتين معاً | — | **98%** · أطول انقطاع **0.27 ث** |

ولأن `drop_pending_updates=false`، فحتى لو توقّف كل شيء فتيليجرام يحتفظ بالرسائل
حتى ٢٤ ساعة ويُسلّمها عند العودة — **لا رسالة تُفقد**.

### أدوات التشغيل (كانت مُجرّبة فعلياً)

```bash
bash scripts/ops_status.sh              # تقرير كامل: العمليات، المنفذ، الويب هوك، الأخطاء
bash scripts/ops_restart.sh             # إعادة تشغيل نظيفة لكل شيء
python scripts/measure_availability.py --kill 2   # إثبات التوفّر رقمياً
python scripts/watchdog.py              # فحص وإصلاح ذاتي (يستعمله الحارس المجدول)
```

### ملاحظة تشخيصية
إحصاءات الأداء في `GET /health` **لكل عملية على حدة** (لأن الذاكرة غير مشتركة)؛
والمهمّ منه للفحص هو `status` و`pending` و`webhook_ok`.

## التشغيل المستمر والمراقبة الذاتية

ثلاثة أدوات تجعل التشغيل بلا تدخّل يدوي:

## الوضع الحاليّ للبوت الأصلي والترحيل من خدمة خارجية

النسخة الحالية في هذا المستودع **جاهزة للتشغيل مباشرة** بـ`python -m app.main`، ولا
تحتاج أي ترحيل تقني. أمّا إن كان للمالك **بوت قائم** يعمل من خدمة أو خادم خارجي
بالتوكن نفسه، فإن نقل العمل إلى هذه النسخة **قرار مالك** لا يُتّخذ تلقائياً: تشغيل
نسختين بالتوكن نفسه يُفسد استقبال التحديثات (polling وwebhook لا يتعايشان بشكل سليم).

الترتيب الآمن — دون كتابة أي توكن حقيقي في أمر أو ملف متتبَّع في Git:

```bash
set -a && . ./.env && set +a   # يقرأ BOT_TOKEN وغيره من .env المحلي فقط

# ١) افحص الحالة الحالية قبل أي تغيير
curl -sS "https://api.telegram.org/bot${BOT_TOKEN}/getWebhookInfo" | python -m json.tool

# ٢) إن اخترت webhook: سجّل العنوان الجديد
curl -sS "https://api.telegram.org/bot${BOT_TOKEN}/setWebhook" \
  --data-urlencode "url=${WEBHOOK_BASE_URL}${WEBHOOK_PATH}" \
  --data-urlencode "secret_token=${WEBHOOK_SECRET}" \
  --data-urlencode "drop_pending_updates=true" | python -m json.tool

# ٣) إن اخترت polling: احذف الـwebhook أولاً
curl -sS "https://api.telegram.org/bot${BOT_TOKEN}/deleteWebhook?drop_pending_updates=true" \
  | python -m json.tool
```

وبدلاً من `curl` يمكن استعمال `python scripts/setup_webhook.py` و`--info` و`--delete`
(وهي لا تطبع التوكن أبداً). وبعد الإيقاف التام للخدمة القديمة يلزم سحب التوكن منها
(`chmod 600 .env` وحذف أي نسخة تحتويه)، والتفاصيل الكاملة في `docs/DEPLOY.md`
(قسم «الوضع الحاليّ للبوت الأصلي»).
